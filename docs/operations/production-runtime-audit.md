### Ten-minute 1,000-VU cache-heavy soak

## Finding R1 — gateway 502 amplification under sustained load

- **Classification/severity:** HIGH DEFECT; resilience defect in the tested two-replica production Compose topology.
- **Reproduction:** From the repository root on a fresh disposable Docker host, run `python ops/load-testing/capacity_runner.py --output ops/load-testing/results/<new-name> --topologies 2 --profiles cache-heavy --vus 1000 --duration 600s --skip-burst`. It uses authenticated synthetic traffic, shared PostgreSQL coordination, and deterministic mock providers. The preceding 60-second ladder also produced isolated gateway 502s at 100 and 1,000 cache-heavy VUs.
- **Observed impact:** 1,907 of 164,401 soak requests failed as 502. The Nginx excerpt shows `recv() failed (104: Connection reset by peer) while reading response header from upstream`, followed by `no live upstreams while connecting to upstream`. Nginx's production upstream uses `max_fails=1 fail_timeout=5s`. Both backends had zero restarts and zero application error-counter increments; nearby sampled direct probes were 200. The initial upstream connection-reset cause is **unconfirmed**. The evidence does support gateway error amplification after upstreams are passively marked unavailable.
- **Smallest plausible remediation:** Reproduce with request-correlated gateway and backend connection logs, identify why established upstream connections reset, and review the `max_fails=1`/five-second passive-failure behavior so one reset per replica cannot briefly exhaust all healthy targets. Keep failover for genuinely dead replicas. Rerun the same ladder and 10-minute soak after a focused fix; do not mix that result into this baseline.

The earlier capacity document also recorded intermittent gateway 5xx on an older commit. This audit's current-main 502 count stands independently; the older result is context, not a substituted pass or failure.

### Gateway resilience follow-up — 2026-09-28

The original 164,401-request failure above remains the before-fix baseline. Work began from `origin/main` at `07a232fd296386c07ffe93bb3084eaef1a70ae4a` on `fix/gateway-upstream-resilience`. The host (Ryzen 9 5900HX, 16 logical CPUs, 33.7 GB RAM), Docker Engine 29.6.2 (16 CPUs, 16.45 GB VM RAM), backend Python 3.14, Nginx 1.31.3, pgvector PostgreSQL 17, k6 2.1.0, pinned base images, two-replica topology, DB pool 1–5 per replica, cache settings, mock providers, k6 profile, 1,000 VUs, think time, and 600-second duration were retained. The starting gateway used `max_fails=1 fail_timeout=5s`, `proxy_next_upstream error timeout`, and two total upstream attempts; Nginx does not automatically replay non-idempotent POST requests after sending them upstream. Two fresh pre-change 600-second runs did **not** reproduce the historical burst: the traced run completed 194,538 requests with zero errors, and the untraced run completed 197,081 requests with zero errors. This limits attribution of any later load-test improvement to the change.

A bounded deterministic test using the production Nginx configuration reproduced the gateway amplification mechanism. With `max_fails=1 fail_timeout=5s`, one deliberately reset POST on each of two still-running peers returned two 502s; a subsequent gateway `/health` returned 502 while both peers continued serving. Thus the passive failure threshold can temporarily exhaust healthy upstreams. It does **not** establish why the original connections reset. The historical logs show two peer resets 144 ms apart followed by `no live upstreams`; backend restarts, application error counters, and sampled direct readiness did not explain the initiating resets.

The production upstream and matching generated smoke/load configurations now use `max_fails=2 fail_timeout=5s`. The threshold allows one transient failure per peer without ejecting both; a genuinely unavailable peer still reaches the threshold. The gateway records a request ID, selected upstream, upstream status and timings, and forwards the ID to the backend. Optional `SEMANTIX_GATEWAY_TRACE=1` emits backend request start/end, completion, cancellation, or exception with that ID. It defaults off and records no tokens, prompts, secrets, or raw payloads. The load runner retains bounded gateway error lines and matching backend trace lines after disposable cleanup.

#### Residual pre-ASGI reset classification

The confirmed **gateway-wide amplification defect is resolved** for the tested two-replica topology: the controlled old configuration exhausted two still-running peers after one reset each, while the new configuration kept `/health` available; genuine stop/failover and recovery still passed. The remaining question is the rare initiating reset, not peer exhaustion.

The retained traced event has this timeline (UTC):

| Time | Evidence |
| --- | --- |
| About 03:58:19.123 | Nginx began the failed POST, inferred from its 0.001-second total duration; the exact client-accept time was not logged. |
| 03:58:19.124458 | Nginx reported `recv() failed (104: Connection reset by peer)` before any response header from backend A at `172.28.0.2:8000`. |
| 03:58:19.124581 | Access log recorded request ID `d0628d47041893b766b789bc573d2207`, status 502, upstream status 502, connect time 0.000 seconds, no header time, upstream response time 0.000 seconds, and total duration 0.001 seconds. |
| Nearest samples | Backend A was ready/healthy at 03:58:16.709 and 03:58:28.575, with zero restarts and application error increments; sampled CPU was 66.78%/64.48% of one core and RSS 92.64/91.04 MiB. Backend B was also ready/healthy nearby; sampled DB connections/active/lock waits were 10/5/1. |

The retained backend trace excerpt contains **no lifecycle record for that request ID**. This supports failure before ASGI request admission; it does not implicate FastAPI. Uvicorn's access log is emitted at response start, so absence of an access line would not independently prove admission failed. Full backend access and Uvicorn connection logs were not retained after disposable cleanup. A late-run TCP sample showed backend A `OutRsts=1` and gateway `EstabResets=1`, both up from zero; these are network-namespace counters, not a packet capture tied to that request.

The production backend starts one Uvicorn 0.52.1 worker with `httptools` 0.8.0, `uvloop` 0.22.1, a five-second idle keep-alive timeout, backlog 2,048, and no configured connection or request-count limit. The pinned Python runtime was 3.14.7. Its inspected HTTP protocol starts ASGI work only after request headers parse; parser errors send 400, and idle connections close after the keep-alive timer. No application exception, process restart, readiness failure, or version-specific bug was established by the retained evidence.

`nginx -T` in the pinned Nginx 1.31.3 image confirmed API proxy HTTP/1.1, `proxy_next_upstream error timeout`, two total upstream attempts, `proxy_read_timeout 330s`, two DNS-resolved peers, `max_fails=2`, and `fail_timeout=5s`. The other proxy timeouts use Nginx's 60-second defaults. A disposable header probe observed HTTP/1.1 with no `Connection: close` header at the backend. [Nginx upstream documentation](https://nginx.org/en/docs/http/ngx_http_upstream_module.html) says this version defaults to a 32-connection upstream keep-alive cache with a 60-second idle timeout; [proxy documentation](https://nginx.org/en/docs/http/ngx_http_proxy_module.html) says POST is not retried after being sent upstream unless `non_idempotent` is enabled. The failed request's immediate reset, rather than a timeout or name-resolution error, and its single upstream address fit that behavior. A stale-connection race near Uvicorn's five-second idle close is plausible, but unproven.

A focused disposable Nginx-to-Uvicorn probe shortened only Uvicorn's idle timeout to one second and sent 1,200 POSTs around that boundary. It observed reused backend connections (164 distinct backend source ports), **1,200 HTTP 200 responses**, and no experimental POST reset. One readiness probe before the test backend started produced a setup-only 502. This experiment did not reproduce the residual failure, so it does not justify changing keep-alive settings or dependencies. Historical Docker events were unavailable after cleanup. Docker Desktop control-plane logs near the event showed event-stream client EOFs but no matching VM network, OOM, or container-failure warning; Windows System had no event in the 40-second window. Those observations neither establish Docker as the cause nor clear the host network. No packet-level socket tuple, conntrack sample, or full connection log was retained.

**Classification: C — RESIDUAL RUNTIME LIMITATION, acceptable for production re-certification with disclosure.** The observed rates were 5/182,681 and 1/196,061 post-change requests, without a gateway-wide burst, backend restart, sampled readiness failure, or correlated application exception. No second production change was made. Reclassify as a confirmed defect if a representative reproduction or packet-level trace ties the reset to a specific Nginx/Uvicorn/socket action, or if a new comparable soak shows materially higher errors, peer exhaustion, failed readiness, or impaired failover. The isolated 502 is still a real client failure; neither all resets nor all 502s are claimed fixed. Production re-certification is a separate activity and was not run here.

## Limits and NO ACTION observations

- **TEST ENVIRONMENT LIMITATION:** The local gateway was bound to loopback HTTP. External TLS termination, production certificate rotation, real reverse-proxy identity configuration, managed secret delivery, hosted-provider quotas, and managed autoscaling were not certified here. Provider boundary contracts and local trusted-proxy behavior were tested; live provider performance was not.
- **TEST ENVIRONMENT LIMITATION:** Active provider drain was exercised, but a deliberately blocked in-flight DB operation during backend shutdown was not. This is a remaining verification gap for any claim of complete shutdown safety.
- **NO ACTION:** Two generation leaders for a cold identical prompt across two replicas are consistent with intentionally process-local coalescing. A third replica is not justified by this run while the shared DB pool is at budget and lock waits are observed. The load balancer still provides availability/failover value independently of throughput gain.
- **NO ACTION:** The provisional managed-autoscaling thresholds remain unvalidated by this Docker Desktop run. The generation-heavy knee and 502 burst argue against tuning a production threshold from one local measurement. No SDK, cache algorithm, SQL, pool-size, or production proxy setting was changed during the baseline.
